\section{Introduction}
\label{sec:introduction}

3D Gaussian Splatting \citep{kerbl2023_3dgs} optimizes an explicit set of anisotropic 3D
Gaussians against photographs by differentiable rasterization.  The optimization is
image-hungry by construction.  Every iteration samples one or more source views and compares
a full render against the stored photograph.  The consequence is easy to overlook on
benchmark scenes and dominant on real capture rigs.  The source images themselves are the
largest resident data structure of the reconstruction.  A camera dome producing tens to
hundreds of high-resolution views per frame quickly exceeds what a single GPU can hold, and
streaming the images from disk trades the memory bottleneck for a storage-bandwidth
bottleneck.  The model being optimized, a few hundred thousand Gaussians, is tiny by
comparison.

This paper asks whether the photographs need to be there at all.  3DGS does not consume
images.  It consumes colors at projected sample locations.  Any representation that can
answer the question which color view $v$ sees at image location $\bm{x}$ can supervise the
optimization.  We therefore fit every input image once, offline, with a compact mixture of
anisotropic 2D Gaussians, called a compact capture, and discard the image.  The capture is
three orders of magnitude smaller than the raw RGB working set (\cref{sec:memory}), analytic,
differentiable, and can be evaluated at arbitrary subpixel locations without decoding,
resampling, or caching full frames.  Our working hypothesis is that compact 2D Gaussian
captures contain sufficient information to supervise reconstruction and refinement of a
standard 3D Gaussian Splatting representation without returning to source RGB.

The resulting pipeline has a hard, checkable data boundary.  After the per-view fit, no stage
of reconstruction opens an image file, imports an image loader, or receives a dense RGB
tensor.  Reconstruction consumes only calibrated cameras plus frozen 2D Gaussian fields.  We
treat this process separation as part of the result rather than an implementation preference,
and we enforce it structurally through typed inputs, import denials, and containment
invariants (\cref{sec:overview}).\evidence{ara/logic/claims.md C31}

The paper follows one thread.  We first show that reconstruction from the 2D fields works
with the standard 3DGS machinery, initialized as usual from random points or from a sparse
SfM point cloud (\cref{sec:reconstruction}), and we define the protocol that measures what
this buys in GPU memory (\cref{sec:memory}).  Because rendering projects the 3D Gaussian
field to per-view 2D Gaussians, the reconstruction problem also admits a more direct
initialization.  Inverting the projection turns every fitted 2D Gaussian into a constraint on
the 3D field, and \cref{sec:tomography} develops this tomographic initialization in closed
form.  The naive inversion fails in identifiable ways, and \cref{sec:refinement} explains the
failures and the corresponding fixes.  \Cref{sec:experiments} evaluates the full pipeline and
closes with the ablation study.  The reconstruction result is established with the standard
initializations alone, so the value of the tomographic initializer is a separate question
with its own evaluation, and a weak initializer outcome does not touch the reconstruction
result.

        2D Gaussian fields (\cref{sec:reconstruction}), including a sparse point rasterizer
        with verified parity against a dense reference renderer.
  \item A controlled protocol for measuring peak GPU memory of dense versus compact
